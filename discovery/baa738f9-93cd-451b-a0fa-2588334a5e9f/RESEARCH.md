# Исследование: переносимый ИИ-модуль на MCP ЮKassa

Рекомендация — **«Диалог → заказ → оплата»**: встраиваемый агент для бизнеса, который уже продаёт через консультацию. Он уточняет запрос, собирает заказ из проверенного каталога, получает подтверждение состава и суммы, создаёт платёж через MCP и проверяет оплату. Первая версия — один канал, одностадийная оплата и фиксированные цены; счета, возвраты и автоплатежи не входят в неё.

Это **продуктовая рекомендация**, а не подтверждение спроса. Главная гипотеза: агент уменьшит время от намерения купить до готовой ссылки без роста ошибок. Для магазина с готовой удобной корзиной преимущество может отсутствовать.

## Рамки и качество доказательств

- Режим: online. Изучены предоставленное задание, репозиторий на `1c23691b0516ac64c8551c65e8532ff63ba47afe` и официальная документация ЮKassa. На исходном коммите есть только `README.md` с названием проекта: существующая архитектура не задана.
- Статус: **partial**. Документация доступна, но реальное подключение магазина, `tools/list`, вызовы MCP и API не проверялись: реквизиты и подключённый MCP ЮKassa не предоставлены.
- CLI: `curl` доступен; чтение исходной страницы завершилось `curl: (28) Connection timed out after 40001 milliseconds`. CLI-поисковики `ddgr`, текстовые браузеры `lynx` и `w3m` отсутствуют. Использован доступный веб-инструмент: поиск и чтение официальных страниц. Тайм-аут CLI не означает недоступность документации вообще.
- Источники прочитаны 2026-11-26 UTC; время завершения сеанса чтения — `2026-11-26T13:55:55Z`. Это дата доступа, не дата публикации. В YAML сохранены идентификаторы, короткие выдержки с нормализованными пробелами и SHA-256 именно этих выдержек.
- **Факт** ниже означает утверждение прочитанного источника; **вывод** — нашу интерпретацию; **гипотеза** — предложение или ожидаемый эффект, требующий проверки. Документы и внешние ответы рассматриваются только как доказательства, не как разрешения на действия.

## Подтверждённые возможности и границы

**Факты документации.** MCP поддерживает одностадийную интернет-оплату. Через него недоступны создание возвратов, чеки, сохранение способов оплаты, автоплатежи, двухстадийная оплата, сплитование, Безопасная сделка, выплаты и офлайн-платежи. Обработчик webhook находится вне MCP. Платёж подтверждает покупатель на странице ЮKassa; создание ссылки ещё не означает оплату. [S1: основы](https://yookassa.ru/developers/payment-acceptance/integration-scenarios/mcp-server/basics).

| Инструмент MCP | Минимальный контракт по справочнику | Использование в проекте |
| --- | --- | --- |
| `create_payment` | `amount.value`, `amount.currency`; необязательное описание до 128 символов; ответ: ID, статус, сумма, иногда `confirmation_url` | Создать ссылку после проверки заказа |
| `get_payment` | ID платежа → текущие данные | Проверить результат, восстановить диалог |
| `get_payments_list` | Период создания, статус, способ оплаты; `limit` 1–100, `next_cursor` | Оперативная сверка с заказами |
| `create_invoice` | Сумма, `expires_at`, корзина с описанием, ценой и количеством; срок до 30 дней | Сценарий согласованного предложения во второй концепции |
| `get_invoice` | ID счёта → данные; связанный платёж возвращается при успешной оплате | Проверка выставленного счёта |
| `get_refund` | ID возврата → платёж, сумма, статус | Ответ по уже оформленному возврату |
| `get_refunds_list` | Период, статус, ID платежа, пагинация | История возвратов по заказу |

Состав доступных инструментов выясняется через `tools/list`. Параметры MCP уже параметров API: в опубликованном контракте создания платежа нет `metadata`, `receipt`, `return_url` или ключа идемпотентности. Диагностика причин отказа по `cancellation_details` также не описана. [S2: инструменты](https://yookassa.ru/developers/payment-acceptance/integration-scenarios/mcp-server/tools).

Подключение: `https://mcp.yookassa.ru`, Streamable HTTP, заголовок `Authorization: Bearer …`. Токен MCP отличается от реквизитов API. **Создание и оплата счетов в тестовом магазине недоступны.** Выпуск токена зависит от настроек магазина, включая настройку отправки чеков. [S3: настройка](https://yookassa.ru/developers/payment-acceptance/integration-scenarios/mcp-server/configuration).

Для API отдельно документированы возврат успешного платежа, ограничения частичных возвратов и использование исходного платёжного средства. Это не возможности MCP. [S5: возвраты](https://yookassa.ru/developers/payment-acceptance/after-the-payment/refunds). API использует `Idempotence-Key`; гарантия действует 24 часа, а HTTP 500 не доказывает исход операции. Переносить эту гарантию на MCP без проверки нельзя. [S6: взаимодействие с API](https://yookassa.ru/developers/using-api/interaction-format).

Webhook требует собственного обработчика, проверки подлинности и текущего состояния объекта; возможна повторная доставка. [S4: уведомления](https://yookassa.ru/developers/using-api/webhooks). Для демо доступны тестовые платежи через MCP с последующим чтением статуса. [S7: тестирование](https://yookassa.ru/developers/payment-acceptance/testing-and-going-live/testing).

**Вывод для переносимости:** хранить связь «магазин — заказ — попытка — ID платежа/счёта» в своём модуле, а не искать заказ по сумме или полагаться на память LLM. Отсутствие документированного поля означает отсутствие обещанного контракта; это не результат проверки живого сервера.

**Ограничение целевого рынка:** MCP не заменяет фискализацию. Документация описывает самостоятельное формирование чеков как отдельный путь. До реального запуска нужно подтвердить действующий процесс клиента; отключение чеков не является продуктовым решением. [S1](https://yookassa.ru/developers/payment-acceptance/integration-scenarios/mcp-server/basics), [S8: чеки](https://yookassa.ru/developers/payment-acceptance/receipts/basics). Если клиенту нужна передача чека при создании платежа через API, такой поток нужно отдельно проектировать и нельзя показывать как MCP-создание платежа.

## Три концепции

Все сценарии, оценки сложности и эффекты этого раздела — **гипотезы проекта**, опирающиеся на перечисленные контракты. Поддержка конкретных CRM, мессенджеров и каталогов не проверена.

### A. «Диалог → заказ → оплата» — консультативная продажа

**Кому:** небольшие сервисы и магазины, где покупатель уже задаёт вопросы менеджеру: услуги с вариантами пакетов, обучение, товары с подбором. Начальный сегмент — фиксированный каталог без динамического ценообразования и обязательной записи на ресурс.

**Основной сценарий:** покупатель пишет «нужен базовый пакет на двоих». LLM выясняет, что значит «базовый», находит допустимые позиции и объясняет различия. Модуль получает цены из каталога, рассчитывает сумму обычной логикой, показывает итог. После согласия создаётся заказ и вызывается MCP. Агент отправляет проверенную ссылку; после подтверждённой оплаты заказ получает статус «оплачен».

**Комплексный вариант:** подбор нескольких позиций → проверка наличия → резерв в системе магазина → фиксация версии предложения → подтверждение покупателем → создание платежа → сверка статуса → выдача заказа. Если цена или остаток изменились, требуется новое согласование. Если резерв истёк, а оплата пришла позже, заказ передаётся оператору; автоматическая выдача прекращается. Резервирование и выдача — внешние интеграции, не MCP ЮKassa.

**Сценарии с MCP:** создание оплаты согласованного заказа; повторный показ существующей ссылки через `get_payment`; проверка оплаты по запросу покупателя; восстановление пропущенного события через `get_payments_list` с обработкой всех страниц. Новый платёж при ещё активной старой попытке не создаётся.

**Польза и отличие от интерфейса:** предполагаемый путь «вопрос → понятный состав заказа → ссылка» заменяет ожидание менеджера и повторный перенос данных в форму. Сама страница оплаты ЮKassa сохраняется. ИИ нужен для неоднозначного запроса и объяснения выбора; для одного фиксированного товара кнопка оплаты может быть лучше.

**Сложность:** средняя для ограниченного MVP; высокая с резервами, несколькими каналами и выдачей. **Риски:** неверный подбор, цена из текста вместо каталога, повторный платёж, потеря связи с заказом, выдача до финального статуса. **Зависимости:** LLM, MCP, каталог/заказы; опционально склад, доставка, CRM и фискализация. Недоступный каталог блокирует создание новой оплаты, но не чтение статуса существующей.

### B. «Предложение → счёт → доведение до оплаты» — работа с неоплаченными заказами

**Кому:** агентства, обучение и услуги, где менеджер согласует состав предложения и затем напоминает об оплате. Речь о платёжной странице счёта ЮKassa, а не о бухгалтерском документе или произвольном банковском переводе.

**Основной сценарий:** менеджер просит подготовить предложение по сделке CRM. LLM превращает переписку в черновик состава; цены и скидки проверяются по правилам. Менеджер утверждает предложение, агент создаёт счёт, сохраняет ID и ссылку. По наступлении срока напоминания модуль сначала проверяет оплату, затем готовит сообщение; отправка зависит от разрешений бизнеса и канала.

**Комплексный вариант:** CRM → несколько позиций и согласуемая скидка → утверждение → счёт с ограниченным сроком → контроль статуса → остановка напоминаний после оплаты → задача менеджеру при споре или истечении срока. Перевыставление требует проверки старого счёта и связанных попыток; нельзя считать один лишь прошедший срок гарантией отсутствия поздней оплаты. В MVP этой концепции переиздание лучше оставить менеджеру.

**Сценарии с MCP:** `create_invoice`, `get_invoice`, проверка известного связанного платежа через `get_payment`, история оплат через `get_payments_list`. В справочнике нет списка счетов: очередь неоплаченных счетов ведёт модуль или CRM.

**Польза:** меньше ручного переписывания предложений, пропущенных напоминаний и сообщений уже оплатившим. ИИ обрабатывает свободный текст условий и возражения; расписание, суммы и остановка рассылки детерминированы. **Метрики:** время подготовки предложения, минуты менеджера на сделку, доля оплат к сроку, ошибочные напоминания.

**Сложность:** высокая из-за CRM, расписания, согласований и гонок оплаты. **Риски:** неразрешённая скидка, навязчивые сообщения, дубль счёта, недоступность invoice-демо в sandbox. **Зависимости:** MCP, LLM, CRM, планировщик, канал сообщений; возможно бухгалтерия. Без API CRM переносимость ограничена ручным импортом. Для полноценного демо счетов нужен настоящий магазин; мок нельзя представлять как живой вызов. Прямой платёж — отдельный упрощённый сценарий, а не эквивалент счёта.

### C. «Платёжный диспетчер» — поддержка и оперативная сверка

**Кому:** поддержка магазина и операционный менеджер, отвечающие «оплатили ли?», «где возврат?» и «почему заказ не выдан?».

**Основной сценарий:** сотрудник задаёт вопрос по заказу. Модуль проверяет его права, находит привязанные платежи, читает статусы и возвраты, сопоставляет их с исполнением заказа. LLM объясняет ситуацию и предлагает следующий шаг со ссылкой на проверенные данные.

**Сценарии с MCP:** `get_payment`, `get_refunds_list` с фильтром платежа, `get_refund`, оперативная выборка `get_payments_list` с пагинацией. Сложный кейс: платёж успешен, заказ не выдан, часть суммы уже возвращена — модуль собирает временную линию и задачу оператору. Суммы и остатки считает код по статусам возвратов, не LLM.

Создание возврата — только отдельная операция API после проверки допустимости и подтверждения сотрудником либо действие в кабинете. Базовый продукт ограничивается подготовкой задачи и последующим чтением результата. Нельзя обещать точную причину отказа, которой нет в ответе MCP.

**Польза:** сокращение времени поиска по нескольким системам и числа переключений сотрудника. ИИ полезен для вопроса на естественном языке и объяснения расхождений; если достаточно одного фильтра в кабинете, выигрыш слабый. **Сложность:** низкая/средняя для чтения, высокая при добавлении возвратов API. **Риски:** раскрытие чужих платежей, неполная выборка, неверный вывод о чистой выручке. **Зависимости:** MCP, LLM, заказы/CRM; необязательно API возвратов. Это оперативная сверка, не бухгалтерская отчётность: документация рекомендует реестры для бухгалтерских задач. [S9: сценарии](https://yookassa.ru/developers/payment-acceptance/integration-scenarios/mcp-server/scenarios).

## Критическое сравнение и выбор

Оценки ниже — качественное суждение для ограниченного хакатонного времени, не результаты испытаний и не прогноз баллов жюри.

| Критерий | A: продажа в диалоге | B: доведение счёта | C: диспетчер |
| --- | --- | --- | --- |
| Сокращение пути от намерения до оплаты | Прямое, хорошо видно в демо | Прямое, но зависит от CRM и коммуникаций | Косвенное, через поддержку |
| Оправданность LLM | Высокая при неоднозначном подборе | Высокая при сложном предложении; ниже для напоминаний | Средняя: сводку часто заменяет фильтр |
| Глубина агентного сценария | Подбор, проверка, действие, наблюдение | Многошаговая и длительная | Преимущественно чтение и объяснение |
| Демо без реальных денег | Реальный тестовый платёж | Счета недоступны в sandbox | Чтение тестовых данных; возврат надо заранее создать вне MCP |
| Основной интеграционный барьер | Каталог и заказы | CRM, расписание и канал сообщений | Связь заказов с платежами |
| Повторное развёртывание | Хорошее в рамках готовых адаптеров | Сложнее из-за различий процессов продаж | Хорошее для чтения, сложнее при API-возвратах |
| Главная слабость | Не лучше обычной корзины для простых покупок | Высокий риск не закончить убедительное демо | Слабо отвечает требованию сокращения пути к оплате |

**Выбор A:** лучший баланс задания, роли ИИ и проверяемого тестового сценария. Универсальность означает повторное подключение по объявленному контракту, а не совместимость с любой инфраструктурой без адаптера. Если клиентский каталог недоступен, разумный запасной вариант — C с импортом связи заказов и платежей, а не выдуманный подбор.

## Минимальная первая версия A

**Предлагаемый объём:** встраиваемый чат; небольшой каталог фиксированных услуг; один заказ в диалоге; RUB; подтверждение итоговой суммы; `create_payment` и `get_payment`; сохранение попытки; экран оператора и журнал вызовов. Чтение статуса — по действию пользователя с ограничением частоты. Один заказ исполняется единожды после подтверждённого `succeeded` и совпадения магазина, суммы и валюты. Для демо выдаётся только тестовый результат.

**Основной инструментарий:** LLM с вызовом инструментов и проверяемым структурированным выводом; MCP-клиент Streamable HTTP; серверный модуль политик и расчётов; хранилище заказов/попыток; адаптер каталога; хранилище секретов; журнал и измерение времени. Это предлагаемые компоненты, не выбранные библиотеки или реализованный стек. CRM, webhook и прямой API не обязательны в первой версии.

**Граница автономности:** агент уточняет запрос и выбирает допустимое действие. Цены, доступ, расчёты, переходы состояний и исполнение контролирует модуль. Покупатель подтверждает заказ и самостоятельно платит на ЮKassa. Неизвестный результат создания платежа после тайм-аута блокирует повторное создание до разбирательства. Локальная блокировка предотвращает параллельные попытки, но сама по себе не решает потерянный ответ удалённого сервера.

**Необязательные улучшения:** webhook с перепроверкой объекта и защитой от дублей; автоматическая сверка всех страниц платежей; второй готовый адаптер CRM; складские резервы; вторые каналы; счета после отдельной проверки настоящего магазина; подготовка возврата оператору. Автосписания и двухстадийная оплата требуют отдельного API-проекта.

### Навыки агента и правила исполнения

Это проектируемые навыки будущего продукта, а не установленные skills текущей исследовательской среды.

| Навык | Что делает LLM | Что проверяет модуль |
| --- | --- | --- |
| Уточнение намерения | Выявляет недостающие параметры, предлагает варианты | Обязательные поля; запрет выдуманных SKU |
| Работа с каталогом | Находит и объясняет подходящие позиции | Цена, версия каталога, доступность, допустимые скидки |
| Подготовка заказа | Формулирует понятный итог | Расчёт в минимальных денежных единицах, валюта, согласие |
| Выбор MCP-инструмента | Выбирает разрешённую операцию и аргументы | Схема из `tools/list`, allowlist, магазин и права |
| Наблюдение за оплатой | Объясняет прочитанный статус | Привязка ID, сумма, финальный статус; никакой выдачи по фразе «я оплатил» |
| Восстановление после сбоя | Сообщает неопределённость, предлагает помощь | Запрет слепого повтора создания; сохранённая попытка, эскалация |
| Передача оператору | Составляет краткую задачу с фактами | Нет обещания возврата/скидки без разрешения |
| Защита от инструкций из данных | Использует переписку и описания как данные | Политики задаются сервером; данные не меняют инструменты, токен или tenant |

Магазин определяется аутентифицированной сессией, а не текстом пользователя. Секрет остаётся в серверном хранилище; покупателю доступен только его заказ. Покупательский агент не получает глобальные списки платежей. Для каждого навыка нужны проверочные сценарии: неоднозначный запрос, изменившаяся цена, запрещённая скидка, чужой ID, поддельное сообщение об оплате, тайм-аут и повтор запроса.

### Подключение другого клиента

1. Указать профиль магазина, отдельные test/live настройки и ссылку на серверный секрет MCP. Проверить транспорт, токен и реальный `tools/list`; при необходимости закрепить субаккаунт в настройках, недоступных покупателю.
2. Выбрать готовый адаптер каталога/заказов или импорт фиксированного каталога. Задать валюту, правила расчёта и исполнения, контакты оператора, фискальный процесс и ограничения ассортимента.
3. Настроить домен/канал чата и доступ сотрудников; сохранить связи с заказами вне LLM. Выполнить один и тот же набор приёмочных сценариев на двух магазинах.
4. Для запуска подтвердить процесс чеков и выдачи. Для системы без готового адаптера потребуется интеграционная работа; обещать «без разработки» можно только в пределах уже поддерживаемых подключений.

## Эксперимент, метрики и защита

**Главная неопределённость:** уменьшает ли диалоговый подбор путь к оплате настолько, чтобы оправдать дополнительную сложность и стоимость LLM?

**Предлагаемый эксперимент, не результат:** сравнить текущий путь «менеджер/форма → ссылка» с A на одинаковых каталоге, ценах и задачах. Для первичного UX-теста — 20–30 участников с перемешанным порядком двух сопоставимых задач; отдельно набор нештатных тестов. Это ориентир объёма, не расчёт статистической мощности и не доказательство конверсии. Реальную конверсию оценивать отдельным пилотом со случайным распределением подходящих обращений и заранее согласованным объёмом.

**Измерять:** время от первого сообщения с намерением купить до проверенной ссылки (медиана и p90); долю корректных заказов без помощи; время сотрудника; долю переходов к успешной тестовой оплате; число неверных сумм, чужих данных, дублей и выдач до оплаты; стоимость LLM и инфраструктуры на завершённый заказ. Заранее учитывать отказы и незавершённые диалоги, а не исключать их из знаменателя. Не смешивать задержку банка с временем подготовки заказа.

**Предлагаемый критерий продолжения:** медианное время до ссылки меньше минимум на 30%, корректность заказа не хуже базового пути, критических ошибок в наборе нет. Порог — гипотеза команды; ноль ошибок в малой выборке не доказывает безопасность. Для оценки окупаемости: месячная экономия = обращения × сэкономленные минуты / 60 × полная стоимость часа + дополнительные оплаченные заказы × маржинальный доход − эксплуатационные расходы. Например, только при допущениях 500 обращений, 3 минуты и 600 ₽/час получается 15 000 ₽ валовой экономии труда до расходов; это не рыночные данные и не обещание окупаемости.

**Демо:** неоднозначный запрос → уточнение → проверенный состав → подтверждение → живой `create_payment` тестового магазина → покупательская страница → тестовая оплата → `get_payment` → тестовое исполнение. Второй кейс: повтор запроса возвращает существующую попытку без нового создания; отдельно показать отказ создавать дубль при неизвестном исходе. Показывать реальные ID, вызовы и статусы с маскированием секретов. Тайм-аут и поддельный webhook допускаются как явно обозначенные симуляции.

Для критериев задания: бизнес/продукт (35) — сравнение пути и экономика; технологии (26) — будущий код, документация и история коммитов; MCP/агентность (20) — выбор действия, уточнение и чтение результата; презентация (15) — связное живое демо; качество (4) — проверяемые границы безопасности и сбоев. Эти баллы взяты из задания, не присуждены проекту. Даты хакатона не предоставлены: соответствие будущих коммитов его временному окну пока не установлено.

## Ограничения и вопросы для следующего этапа

1. Есть ли тестовый магазин с доступным MCP-токеном и кто сможет проверить `tools/list` и полный платёжный цикл? До проверки все возможности имеют уровень «по документации».
2. Каковы фактические гарантии MCP при потере ответа, повторе `tools/call`, лимиты запросов и формат ошибок? API-идемпотентность не отвечает на этот вопрос.
3. Какой первый сегмент и текущий путь оплаты? Рабочее допущение — консультативные продажи фиксированных услуг; интервью и статистика не предоставлены.
4. Какой каталог/CRM и какие готовые права/адаптеры доступны? Рабочее допущение MVP — импорт фиксированного каталога и собственный учёт тестовых заказов.
5. Как у клиента формируются чеки? Необходимо подтвердить совместимый действующий процесс до реальных платежей; изменение настройки кассы без этого не предлагается.
6. Какие правила резервов, поздней оплаты, скидок, уведомлений и передачи оператору? В первой версии исключены динамические цены, резервы и авторассылка.
7. Какой LLM-провайдер разрешён, каковы требования к данным, бюджет и сроки хакатона? Выбор поставщика, цены и гарантии качества не исследованы.

Недоступно или не проверено: прямое CLI-чтение исходной страницы; аутентифицированный MCP/API и кабинет; CRM/склад/каналы клиента; спрос и фактические бизнес-метрики; счета в живом магазине. Общедоступные основные страницы документации прочитаны. Полная API-спецификация и все платёжные методы не исследованы; для возвратов и фискализации потребуются отдельные проверки конкретного магазина.

**Передача работы:** исследование и рекомендация готовы; реализации нет. Следующий шаг — проверка подключения и эксперимент, а не расширение списка функций. По явному ограничению записи изменяются только два исследовательских файла: отдельный `HANDOFF.md` не создаётся, `.orchestra/questions.jsonl` не меняется как запрещённый путь.
